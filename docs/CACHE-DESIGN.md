# 缓存设计规范（第五章 5.1 ~ 5.3）

> 本文件是**缓存层的规格说明**：Key 怎么命名、Value 存什么、TTL 怎么定、写操作之后
> 删哪些 key、Redis 挂了怎么办、收益怎么量化。
> 阶段路线与进度看板见 [`PLAN.md`](PLAN.md)，本文件只讲缓存本身。
>
> 配套实现：`src/service/CacheKeys.h`（Key 唯一构造入口）、`src/service/SkuCache.*`（Redis 封装）、
> `SeckillService::listSkus / detailSku / doSeckill`（读写路径）。
> 配套压测：`scripts/read-bench.sh`、`jmeter/read-baseline.jmx`。

---

## 1. 为什么现在才加缓存，以及加在哪

阶段一压出来的基线是 **440+ QPS / 0 超卖**，瓶颈定位在 `seckill_sku` 的行锁串行化——
那是**写**接口（下单）的问题。但同一时刻还有两个**读**接口在被反复调用：

| 接口 | 路径 | 每次调用做了什么 | 洪峰期的荒谬之处 |
| --- | --- | --- | --- |
| 商品列表 | `GET /api/seckill/list` | `SELECT` 全部商品（20 行） | 一万个用户同时刷新列表，MySQL 就把同一条 SQL 执行一万遍，返回一模一样的结果 |
| 商品详情 | `GET /api/seckill/{skuId}` | `SELECT` 单行 | 同一个 sku 被查几千次，每次都让 InnoDB 走一遍索引 |

读请求的特点决定了它是缓存的最佳对象：**结果重复、允许短暂陈旧、不参与正确性判断**。
下单接口则相反——它必须落在 MySQL 上拿行锁做原子扣减，缓存替代不了真相源。

所以第五章的加缓存范围是**读接口**，写接口（下单）只多了一个动作：成功后让缓存失效。

## 2. Key 设计规范

### 2.1 模板

```
<prefix>:<biz>:<version>:<type>[:<id>]

seckill:sku:v1:list          # 商品列表（全量，不分页）
seckill:sku:v1:item:1001     # 单个商品详情
seckill:sku:v1:stock:1001    # 库存计数（阶段四 7.2 启用，当前只占位不读写）
```

### 2.2 六条规则及其代价

| # | 规则 | 违反之后会发生什么 |
| --- | --- | --- |
| 1 | **必须带业务前缀** | 同一个 Redis 上还住着 `sess:` / `sms:code:` / `login:fail:` / `reg:ip:`（见 §2.3）。没有前缀，出问题只能 `FLUSHDB`——那会顺手踢掉所有人的登录态 |
| 2 | **必须带结构版本号** | JSON 结构改了不升版本，发布瞬间旧结构被新代码读到 → 解析全崩。升了版本则新旧 key 并存到自然过期，**不需要清库**（清库 = 主动制造一次缓存雪崩） |
| 3 | **全小写、尽量短** | key 本身占内存。100 万个 key，每个多 10 字节就是 10MB |
| 4 | **绝不放易变维度** | 把 TTL、时间戳、userId 拼进 key，命中率直接趋零、内存无上限增长。这是新手最常踩的一条 |
| 5 | **不分页就不带分页参数** | 列表缓存是全量（`LIMIT 100`）。真要分页时再开 `...:list:{page}`，且必须限死最大页数，否则攻击者用随机 page 打爆内存 |
| 6 | **冒号分段** | 运维可以 `SCAN 0 MATCH seckill:sku:v1:item:*` 精确定位一类 key；`KEYS` 在生产是禁用的（单线程全量遍历，会卡住 Redis） |

### 2.3 本项目 Redis Key 全量盘点

| Key | 用途 | TTL | 引入章节 |
| --- | --- | --- | --- |
| `sess:{jti}` | 登录会话（可吊销） | 与 JWT exp 对齐（7200s） | 3.2 |
| `sms:code:{phone}` | 短信验证码 | 300s | 3.3 |
| `sms:cd:{phone}` | 重发冷却 | 60s | 3.3 |
| `sms:try:{phone}` | 验证码试错次数 | — | 3.5 |
| `sms:day:{phone}:{day}` | 每日发送上限 | 跨天 | 3.5 |
| `login:fail:{phone}` | 密码错误计数 | 600s | 3.6 |
| `login:lock:{phone}` | 账号锁定标记 | 600s | 3.6 |
| `reg:ip:{ip}` | 同 IP 注册计数 | 3600s | 3.1（ADR-6） |
| **`seckill:sku:v1:list`** | **商品列表** | **30s + 抖动** | **5.2（本次）** |
| **`seckill:sku:v1:item:{id}`** | **商品详情 / 空值占位** | **60s + 抖动 / 60s** | **5.3（本次）** |
| `seckill:sku:v1:stock:{id}` | 库存原子计数（未启用） | — | 7.2 预留 |

> **历史包袱要说清楚**：前 8 个 key 是第三章登录模块引入的，没有 `seckill:` 前缀、没有版本号。
> 这是既有事实，本次不改动它们（改了要同时动会话、验证码、限流四个模块，收益为零、风险不小）。
> 规矩是：**从第五章起新增的 key 一律遵守新规范**，历史 key 在阶段四统一迁移。

## 3. Value 设计

### 3.1 存紧凑 JSON 字符串，不存 Hash

| 方案 | 读 | 写 | 为什么不选 |
| --- | --- | --- | --- |
| **String（紧凑 JSON）** ✅ | 1 次 `GET` 拿到完整对象 | 整值覆盖 / `DEL` | — |
| Hash（`HGETALL`） | 1 次 `HGETALL` 再拼装 | 可字段级更新 | 商品详情是**整体失效**的语义，字段级更新反而会造出"改了 name 忘了改 stock"的半更新态；且 `HGETALL` 对大 hash 同样是 O(n) |

紧凑（`indentation=""`）而不是带缩进：20 条商品的列表，带缩进约 4KB，紧凑后约 2.6KB，**省 35% 内存与网络字节**。

### 3.2 大 key 边界

| 项 | 量级 | 结论 |
| --- | --- | --- |
| 单条商品 JSON | ≈ 130 B | — |
| 列表（20 条，紧凑） | ≈ 2.6 KB | 安全 |
| 列表上限（`LIMIT 100`） | ≈ 13 KB | 仍是 string 小 key |

Redis 的"大 key"通常指 string > 100KB，或 hash/list 元素过万。列表缓存**上限锁死 100 条**
（`LIMIT 100` 写在 SQL 里，不是靠约定），所以这个 key 不会长成大 key——这是有意的自我保护。

> **大数据量级印证**：压测种子 `sql/seed_sku.sql` 默认 **20 万条**商品，列表接口仍只返回前 100 条、`value ≈ 13KB`——无论总量 20 条还是 20 万条，列表缓存体积恒定，正是 `LIMIT 100` 自我保护要的效果。详情 key 基数则随总量到 20 万，命中率/内存占用才测得出来。

### 3.3 空值哨兵（防缓存穿透，对应 5.6，本次提前落地）

```
GET /api/seckill/999999   →  DB 查无此行  →  SETEX seckill:sku:v1:item:999999 60 "__nil__"
```

业务 value 只可能是 JSON 对象或数组，一个裸的 `__nil__` 字符串不可能是合法 JSON，
所以拿它当哨兵不会和真实数据混淆。TTL 用最短的一档（60s）：

- 设长了：新品上架后要等几分钟才能被查到（一致性损失）；
- 设短了：穿透防护变弱。
- 60s 的实际效果：攻击者用随机 id 打库，**每个 id 每分钟最多穿透一次**——足以把"打穿"变成"打不穿"。

> 为什么不用布隆过滤器（5.7 的内容）：布隆过滤器解决的是"id 集合海量且基本不变"的穿透；
> 秒杀商品是几十到几百个、还会上下架，空值缓存性价比更高且没有误判。等商品量级上去再引入。

## 4. TTL 与抖动

| Key | 基准 TTL | 抖动 | 为什么是这个数 |
| --- | --- | --- | --- |
| `list` | 30s | +[0,30)s | 列表含全部商品的 stock，是聚合值，陈旧容忍度最低用短 TTL 补 |
| `item` | 60s | +[0,30)s | 单品，且下单后会主动 `DEL`，TTL 可以放宽 |
| 空值 | 60s | +[0,30)s | 见 §3.3 |

**抖动是必须的，不是可选优化**：没有抖动时，缓存预热起来的那批 key 会在同一秒集体失效，
全部请求瞬间回源数据库——这就是**缓存雪崩**。抖动把"同一秒"摊平到一个 30 秒的窗口里。

实现用 `thread_local std::mt19937`：Drogon 的 handler 跑在多个 IO 线程上，
共享一个 `rand()` / 全局 `mt19937` 会构成数据竞争（UB），每线程一份则无锁无竞争。

## 5. 读写路径（Cache-Aside）

### 5.1 读

```
请求 → GET key
        ├─ 命中        → 解析 JSON → 返回（数据库全程没被碰到）
        └─ 未命中/异常 → 查 MySQL → 回写 SETEX（fire-and-forget）→ 返回
```

未命中的三种情况（**统一按"未命中"处理，不细分**）：

| 情况 | 处理 |
| --- | --- |
| Redis 回 `nil`（真没缓存） | 回源 |
| Redis 不可用 / 超时 | 回源（fail-open，见 §7） |
| 缓存里的值解析失败（版本串了 / 被人工改坏） | **删掉这个 key** 再回源 —— 留着只会让每次读都白解析一次 |

### 5.2 写（下单成功后失效）

```
事务 commit 成功 → DEL 缓存 key
```

**顺序绝对不能反**。反序（先 `DEL` 再更新数据库）的经典事故：

```
1. 写请求 DEL 缓存
2. 读请求进来，miss，回源读到【旧值】，写回缓存
3. 写请求更新数据库完成
→ 缓存里的旧值要等 TTL 到期才自愈，中间所有读请求拿到的都是错的
```

代码里 `DEL` 挂在事务的 `setCommitCallback` 里，`committed == true` 才执行，
**天然保证"数据库先落定"**。

### 5.3 删哪些 key：一次真实的取舍

| 策略 | 配置值 | 命中率 | 库存新鲜度 | 适用 |
| --- | --- | --- | --- | --- |
| 只删详情 | `item`（**默认**） | 高 | 详情页准，列表页允许陈旧 | 真实秒杀：列表页本就该静态化，"列表里还剩几件"对下单决策没有意义 |
| 详情 + 列表都删 | `all` | **趋零** | 最准 | 不推荐：列表是全量聚合 key，**任意一个 sku 成交都会删它**，写 QPS 一高，这个 key 等于不存在 |
| 谁都不删 | `none` | 最高（压测数字最好看） | 最差 | 只在"库存展示完全不敏感"时用；售罄后用户最长 TTL 秒内仍看到"还有货" |

默认值选 `item`，理由写在上表里了。这个开关存在的意义是：**把取舍显式化**，
而不是悄悄写死一个行为让后面的人猜。

> 5.4 会展开：即便顺序对了，并发下仍有一个极窄窗口能让旧值回填（读请求在 `DEL` 之前
> 读到旧值、在 `DEL` 之后才写回缓存）→ 延迟双删。当前实现的残留不一致窗口 = 一次 DB 查询时间。

## 6. 缓存的三个经典问题，当前各自到哪一步

| 问题 | 现象 | 当前对策 | 章节 |
| --- | --- | --- | --- |
| 缓存穿透 | 查不存在的 key，绕过缓存直打 DB | ✅ 空值哨兵（§3.3） | 5.6（已提前落地） |
| 缓存雪崩 | 大批 key 同时失效，请求集体回源 | ✅ TTL 随机抖动（§4） | 5.5 相关 |
| 缓存击穿 | 单个热点 key 失效瞬间，所有请求同时回源 | ❌ 未处理 | 5.5 之后（互斥重建 / 逻辑过期） |

击穿为什么现在不做：热点 key 失效后，并发回源的是**同一个 sku 的单行主键查询**，
MySQL 扛得住（不是行锁竞争，是共享读）。真正的代价只是一次慢查询，不值得为它引入
互斥锁的复杂度。**先量清楚再优化**——这是本项目一贯的顺序。

## 7. 失败策略：缓存必须 fail-open

| 组件 | Redis 挂了怎么办 | 判据 |
| --- | --- | --- |
| `SessionStore`（会话校验） | **fail-close**：拒绝 | 错放一次 = 被封禁的 token 能继续下单，安全事件不可逆 |
| `SkuCache`（商品缓存） | **fail-open**：当未命中，回源 DB | 错放一次 = 这个请求多查一次库，慢一点，**无任何正确性损失** |

同一个系统里两个组件对"Redis 挂了"做出相反反应，这不是双标，是因为**代价结构不同**。
判据只有一句：**误放的代价 vs 误杀的代价，哪个更大就防哪个**。

> 鉴权要收紧（宁可误杀），限流要放松（宁可放过），缓存要放行（宁可慢）。三者不能混为一谈。

Redis 客户端不可用时，`SkuCache::enabled` 被强制置 false，读请求直连 MySQL——
服务**不会**因为缓存中间件没装就整站 500。

## 8. 可观测：没有计数器的缓存等于没做

`GET /api/cache/stats`：

```json
{
  "code": 0,
  "data": {
    "enabled": true,
    "hit": 18422, "miss": 41, "err": 0, "write": 41,
    "hit_rate": 0.9978,
    "keys": { "list": "seckill:sku:v1:list", "item_sample": "seckill:sku:v1:item:1" },
    "ttl": { "list": 30, "detail": 60, "null": 60, "jitter": 30 },
    "invalidate_on_order": "item"
  }
}
```

- `miss` 就等于"这一段时间回源了几次数据库"——它是缓存收益的直接度量。
- `err > 0` 说明 Redis 在报错，此时的高 QPS 是假象（实际都在回源）。
- keys 直接回显，可以拿去 `redis-cli GET <key>` / `TTL <key>` 人工核对。

## 9. 基线压测方法

```bash
# 前置：MySQL + Redis 都在跑、已编译、已导入种子数据
mysql -h127.0.0.1 -useckill -pseckill seckill < sql/seed_sku.sql   # 20 条商品

bash scripts/read-bench.sh            # 默认总并发 100 × 60s
bash scripts/read-bench.sh 200 30     # 总并发 200 × 30s
export JMETER_BIN=/opt/apache-jmeter-5.6.3/bin/jmeter   # 可选：出 HTML 报告
```

**方法论**：同一套流量跑两轮，只改 `cache.enabled` 一个变量（脚本自动改配置、重启服务、
清缓存、预热、采集）。`off` 轮是 5.1 的接口基线，`on` 轮是 5.2 / 5.3 的成果。

| 口径 | 说明 |
| --- | --- |
| 并发分配 | 列表 60% / 详情 40%（与 `.jmx` 的双线程组一致） |
| `on` 轮预热 | 先打一轮把缓存填上，测的是**稳态命中**，不是冷启动。冷启动数字要单独标注 |
| 命中率取增量 | 压测前后各读一次 `/api/cache/stats` 取差值，避免把预热阶段的计数算进来 |
| 详情用随机 id | `${__Random(1,20,)}`。只打同一个 id 是"热点 key"benchmark，不是缓存层 benchmark |

**已有坑位（脚本里都做了防御）**：
改了 config 没重启 → 两轮数字一模一样（脚本会核对服务端实际 `enabled`）；
Java 把 `http_proxy` 当代理 → 100% connection refused（跑 JMeter 前 `unset`）；
WSL 上 HC4 初始化失败 → 0 样本（`.jmx` 里强制 `implementation=Java`）；
强杀服务留下的 InnoDB 未回滚事务持行锁 → 数字集体失真（压测前确认 MySQL 干净）。

## 10. 本次实现的已知不足

诚实清单，每一条都对应后续章节：

1. **单 `DEL` 有残留不一致窗口**（§5.2）→ 5.4 延迟双删。
2. **无缓存预热**：进程刚启动时缓存是空的，第一批请求全部回源 → 5.5。
3. **无击穿保护**：热点 key 失效瞬间并发回源（当前可接受，见 §6）→ 5.5 之后。
4. **无布隆过滤器**：空值缓存对"海量随机 id"仍有内存成本 → 5.7。
5. **单级缓存**：每次命中都要走一次 Redis 网络往返（约 0.2~0.5ms）→ 5.8 加本地 LRU 做多级。
6. **库存字段的可缓存性本身是有争议的**：`stock` 是强实时字段，当前靠短 TTL + 下单 `DEL` 兜底。
   阶段四（7.10）会把它拆成独立的 `stock:{id}` 计数，由 Redis 直接承载，届时列表/详情里的
   stock 将改为实时拼装，不再是缓存里的陈旧值。
